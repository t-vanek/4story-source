## Original identity contract and allocator boundary

The original game protocol carries account, character and session IDs as DWORD, including `CS_LOGIN_ACK` (`Lib/Own/TProtocol/include/CSProtocol.h:14–20`) and `CS_CONNECT_REQ` (`:144–149`). Actual `Server/TLoginSvr/DBAccess.h:15–34` declares DWORD output storage for the account, character and key in `CSPLogin`. Original `TGLOBAL.TLogin` declares the matching parameters INT, obtains the account from the row and assigns `@dwKEY = @@IDENTITY` after inserting `TCURRENTUSER` (`_rewrite/docs/schema/procs/TGLOBAL_RAGEZONE/TLogin.sql:161–181`).

The decisive source binding contract is `Lib/Own/TNetLib/TNetLib/SqlBase.cpp:289`: the `BindParam(..., unsigned long* ptr)` overload uses **SQL_C_SLONG, SQL_INTEGER** on the supplied DWORD storage. It preserves the signed32-bit SQL interpretation of the same four bytes; it does not widen the wire DWORD to a positive64-bit SQL number. Reconstructed source DDL likewise has signed `int IDENTITY(1,1)` account/session/character columns (`database/legacy-reconstructed/TGLOBAL_RAGEZONE.tables.sql:25/420`, `TGAME_RAGEZONE.tables.sql:298`). These are saved source/schema artifacts, not freshly extracted backup contents.

| Nonzero wire bits | Matching SQL INTEGER identity | Existing unsigned wire-key BIGINT receipt |
| --- | --- | --- |
| `0x00000001` | `1` | `1` |
| `0x7fffffff` | `2147483647` | `2147483647` |
| `0x80000000` | `-2147483648` | `2147483648` |
| `0xffffffff` | `-1` | `4294967295` |

Zero remains the missing/uninitialized identity sentinel and is rejected by the applicable claim boundaries. Signed storage does not imply that normal allocators generate negative IDs. Source `TGAME.TCreateChar` inserts into signed INT identity and returns `@@IDENTITY` (`TCreateChar.sql:167/236`). Native migration008 account/key identities are INTEGER GENERATED BY DEFAULT, with no positivity constraint on existing account/key rows; native migration012 separately declares character INTEGER GENERATED ALWAYS with `CHECK(dwCharID>0)`. Native `PostgreSQLCharService::CreateOnce` inserts/returns that identity; it does not wrap or reseed it. This slice supports existing nonzero account/session bit patterns with the existing positive character allocator. It does **not** establish high-bit character allocation, sequence rollover, negative character import, or facts about missing backup values. No migration070 is needed or justified for the binding repair.

## Two existing PostgreSQL key domains, not one blanket cast

| Published column family | Actual storage contract | Required binding |
| --- | --- | --- |
| `TCURRENTUSER.dwKEY`, `TLOG.dwKEY`, account/character ownership and child IDs | Signed INTEGER, matching source SQL INT. | `bit_cast<int32_t>(wire DWORD)` for wire-origin identities; already signed SQL outputs stay signed. |
| Migration015 `map_handoff`,016 `map_sessions`,018 `map_checkpoints`,020 `map_transfers` session keys | INTEGER, with actual ownership/current-user relationships. | Signed32-bit identity key. |
| Migration066 social mutation key,067 soulmate offers including target key,069 chat-ban mutation key | INTEGER. | Signed32-bit identity key. |
| Migration035 `accepted_skill_casts`,036 `skill_finish_operations`,037 `skill_action_operations`,040 `skill_purchase_operations`,041 `title_selection_operations`,045 `quest_operations` session keys | BIGINT preserving the nonnegative DWORD wire value; published range checks use0/1 through4294967295. | Positive `long long` widening of the wire key for both insertion and receipt lookup. |
| Migration042 `secure_codes.unlocked_key` and `secure_code_operations.session_key` | BIGINT wire-key domain; unlocked key has0..4294967295 check. | Positive wire key, including unlock comparison/reload and disabled/unlocked0 logic. Account ID stays signed INTEGER. |
| Migration060 `mail_notifications.session_key` | Nullable BIGINT operational receipt. | Positive wire key on actual notification commit. |
| Migration029 `lt_dwkey1..11` | Generic event DWORD payload fields in BIGINT, not session identity foreign keys. | Preserve their existing payload representation. |

Static schema searches found no corresponding user_id/char_id BIGINT column family requiring a second account/character domain. Item IDs, receipt IDs, connection IDs, epochs, revision/deadline/tick values and endpoint IPs have their own contracts and are not arguments for applying the identity helper.

A critical intermediate implementation error was found and handed to both owners: changing every `c.key` alias to signed32-bit also changed gameplay receipt writes/probes and secure unlock values. High-bit keys would then fail their existing BIGINT range checks or fail to find the prior wire-key receipt. The correction keeps explicit signed identity-key and positive wire-key aliases in each mixed function. In particular, a cast validates `TCURRENTUSER` with the signed key but writes/looks up action/cast receipts with the positive key; secure-code account locking uses signed account/current-user identity while `unlocked_key` and its comparison retain the positive value. Published schemas and operational records are preserved, not rewritten to conceal this distinction.

## Login boundary review

Native `SociAuthService::Authenticate` already loads account/session SQL outputs into `int`, binds signed account values, and returns the session bits as `uint32_t` (`soci_auth_service.cpp:382/638`). Its authenticated account DTO is `int32_t`; handlers write DWORD account bits (`handlers.cpp:513`) and retain key bits. Agreement/password/security retry and native session terminator guards use zero as the sentinel. `soci_session_terminator.cpp:61–79` converts the DWORD key to signed32-bit for actual ownership/current-user queries; it must not reject a negative nonzero account or confuse it with a bigint generation.

Two native barriers were actual defects: `PostgreSQLCharService::LockSession` rejected `user<=0` and widened the key positively; `SociMapServerLocator::StartAuthorized/StartNative` rejected negative account IDs and widened the key. Root changed these to user==0 and explicit signed32-bit key conversion. The separate `request.char_id<=0` allocator/schema boundary remains. Static review of Create/List/Delete/rename/session ownership call sites and Login authenticated-user guards found no additional same-domain positivity gate requiring expansion of this slice. The root changes preserve locks, transaction/owner fencing, routing, exact current-user ownership and uncertain handoff reuse; they do not bypass authorization or mint new identities.
