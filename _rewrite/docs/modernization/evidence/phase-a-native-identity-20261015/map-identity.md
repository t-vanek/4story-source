## Exact representation boundary

The source client/Map packets and native `MapSessionClaim` carry account, session and character identity as DWORD/`std::uint32_t`. Original Login identity outputs use SQL INT, and the corresponding archival columns preserve signed INT bits. Native `008-native-login.sql` declares account/current-user keys as GENERATED BY DEFAULT `integer` and does not reject explicitly stored negative account/session bit patterns. The previous native Map code widened these unsigned wire identities to positive `long long`, causing a different numeric value to be compared with the signed INTEGER row.

`services/native_identity.h::SqlInt32Identity` now performs an explicit constexpr `std::bit_cast<std::int32_t>` **only for a source DWORD identity bound to a PostgreSQL INTEGER column**. For example, wire `0x80000000` maps to SQL INTEGER `-2147483648`, and wire `0xffffffff` maps to INTEGER `-1`. On reads, existing signed-int to `std::uint32_t` conversions restore the original bits. Wire DTOs, registry keys, packet layouts, fingerprints and opaque transfer bodies remain unsigned/original bytes.

Column type, not the name `key` or `session_key`, decides the representation. Several newer operational receipts deliberately store the same source session key as unsigned-range BIGINT. Their values remain `2147483648` / `4294967295` for the examples above. Mixed functions now name this value `wire_key` separately from the signed current-user identity bind; both representations refer to the same original session bits in their own existing schemas. No receipt canonicalization, data rewrite or migration was added.
