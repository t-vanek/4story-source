## Admission finding and preserved prerequisite

The initial continuation investigated the actual `MW_CONNECT_ACK` path. It cannot be replaced by a partial admission switch or a newly invented acknowledgement. The selected implementation continuation is consequently the independent basic party flow over the retained, documented RW-as-Map registration extension. This does not complete original Map admission.

* Original Map `SSSender.cpp:210–222` emits `MW_CONNECT_ACK = MW_BASE+1`: `WORD MAKEWORD(server_id,SVRGRP_MAPSVR)`, `BYTE logical_map.size()`, then `BYTE(key)` for every sorted map entry. World `SSHandler.cpp:592–617` consumes that identity and count, rejects duplicate full IDs, and registers the peer. There is no distinct application acknowledgement. A completed TCP write proves delivery to the local transport, not World application acceptance or Map bootstrap projection.
* Map `TMapSvr.cpp:2499–2573` loads physical channels/maps/units from `CTBLServerChart`, initializes each physical channel, and fills `m_mapTLOGCHANNEL` from `CTBLChannelChart`. The latter query (`DBAccess.h:26–51`) joins `TCHANNELCHART` to `TSVRCHART` on map, group, unit, and physical channel, filters only `bServerID`, and groups map/logical/physical/server. The surrounding construction has no separate PvE/BOW/BR logical-channel filter. Source mode IDs are `BOW_SERVER_ID=30`, `BR_SERVER_ID=50` (`NetCode.h:143,146`).
* The key is `MAKELONG(WORD map_id,WORD logical_channel)` but the sender truncates it to a byte. It therefore sends the low byte of the map ID, rather than the logical channel. Duplicate bytes collapse in World's map, and a source count exceeding255 would wrap while the producer still writes every entry. These quirks require explicit source/capability decisions; an inferred configuration-channel list is not the source oracle.
* Existing PostgreSQL routing publication014 derives `route_compat.TSVRCHART` by the original `TUNITCHART`/`TMAPCHART` join and exposes `TCHANNELCHART`. `activate_routing_catalog.py:12–65` requires the complete pinned, verified reference manifest and checks actual values/raw-byte checkpoints. It rejects ambiguous cell owners and preserves source gaps. Map `postgresql_map_route.cpp:10–23` already uses the same join with an explicit `app_world.routing_worlds.source_group` mapping; it does not establish the anomalous source registration bytes by itself.
* Previously recorded reconstruction metadata (`_rewrite/docs/database-reconstruction/evidence/data-profiles.json:1059,1164,1696,2326`) reports battle-time5, logical-channel361, map301, and unit361 rows. This is read-only documentary evidence, not a newly queried count or reconstructed registration byte vector. No values were re-extracted in this continuation.
* World `SSHandler.cpp:619–699` sends, in order: local/castle status, mission status, compiled SKYGARDEN status, applicable BOW/BR initialization, conditional relay-connect, each event, each cash sale, each guild/castle applicant count, one-time guild tactics expiry setup, month ranks, and tournament information. The local and mission consumer packets drive gameplay timers, rather than representing a generic ready response. An empty event set cannot remove the other mandatory bootstrap branches.
* Original `CTBLBattleTimeChart` (`World DBAccess.h:639–660`) reads eight exact columns of `TBATTLETIMECHART`. Reconstructed schema (`TGAME_RAGEZONE.tables.sql:118–129`) uses byte type/day/week and five signed SQL `int` columns read as source unsigned DWORDs. World initialization (`TWorldSvr.cpp:1298–1355`) also overrides local peace duration180 and modifies the mission schedule using custom times. Its `mapCLOSE.find(2)->second` branch can dereference a missing entry; it must not be converted into guessed schedule values.
* At baseline there is no complete native battle-time registry or authoritative native startup replacement for all guild/war/rank/tournament bootstrap repositories. Existing World main still constructs legacy SOCI repositories. Missing authority and Map consumers remain OPEN. Plain16 framing from the preceding continuation is retained; the modern RW-as-Map extension and its corrected DWORD server-message key are explicitly distinct from source MW admission.

## Original basic party contract

All party membership and invitations are transient World process state (`CTParty`, `m_mapTParty`); source ADD/JOIN/DEL performs no SQL party mutation. Native PostgreSQL is required for live actor authority, identity, protection, and generation validation. Introducing a fabricated durable party table is unnecessary for this source contract.

### Client requests and Map gates

`Map CSHandler.cpp:3419–3504`:

| Request | Exact body | Source gates and forwarding |
| --- | --- | --- |
| `CS_PARTYADD_REQ` | STRING target, BYTE obtain | Current main with a map; BR compile mode drops; arena ID drops. Forward own canonical name, target, obtain, and actual maxHP/HP/maxMP/MP. |
| `CS_PARTYJOIN_REQ` | STRING origin, BYTE obtain, BYTE response | Main; BR compile mode drops. Forward origin, own name, obtain/response, and actual four stats. |
| `CS_PARTYDEL_REQ` | DWORD member | Main with map and party; leaving self allowed, removing another requires own chief ID. Forward WORD party, DWORD member, BYTE kicked(issuer!=member). |

The original Map senders are `SSSender.cpp:2671–2753`. `MW_PARTYADD_ACK` adds STRING origin before target and four DWORD stats after obtain. `MW_PARTYJOIN_ACK` adds STRING target after origin and the same stats after obtain/response. `MW_PARTYDEL_ACK` has no explicit issuer/key fields; the new authority guard must infer self for kick0 and current party chief for kick1, then verify that inferred actor belongs to the incoming typed current Map peer.

Source enum values (`NetCode.h:222–227,390–404,1960–1968`): ASK yes0/no1/busy2; PARTY agree0/deny1/busy2/no-user3/no-requester4/waiters5/already6/full7/not-chief8/no-party9/change-chief10/country11. Obtain free0/solo1/hunter2/lottery3/chief4/order5. Source server ADD/JOIN has no explicit obtain range check; rejecting out-of-enum bytes is modern hardening and must not be described as an existing source check. Original client normally starts at ORDER5 (`TClientGM.cpp:515–591`) and echoes the invited obtain value when answering.

`MWProtocol.h:143–159,197` supplies ADD req/ack `MW_BASE+0x18/0x19`, JOIN `+0x20/+0x21`, DEL `+0x22/+0x23`, MANSTAT `+0x24/+0x25`, ATTR `+0x4A`. `CSProtocol.h:909–956` supplies client offsets `CS_MAP+0x40..0x48` in ADD request, ADD response, JOINASK, JOIN request, JOIN response, DEL request, DEL response, MANSTAT, ATTR order. Actual source senders/client consumers take precedence over incomplete header comments (JOIN has a final class byte).

### World validation and one-use invitations

`World SSHandler.cpp:2486–2621`: source resolves names through `FindTChar`, uppercased in `TWorldSvr.cpp:2736–2748`. Missing inviter/self invite drops. Missing target -> no-user; target waiter -> waiters; target party -> already; unequal effective war country -> country. Existing inviter party requires chief, size<7, and no arena. Only after these gates does source update requester combat stats, send the target ADD request, and set its waiter flag.

`World SSHandler.cpp:2623–2815`: response clears target waiter, handles missing origin/target, relays non-YES response to origin, rechecks target party and both countries, updates target stats, requires both main peers, then rechecks inviter chief/full/arena. It joins the existing party or creates a new party and joins origin first, target second. `JoinParty` (`TWorldSvr.cpp:2930–2987`) separately refuses crossing into/out of BOW30 or BR50 unless both main IDs match.

The original waiter boolean does not prove a particular accepted invitation. Modern authorization must bind one pending invitation to exact origin/target TChar generations, non-recycled keys/current primary peers, and obtain value; consume it once on an answer, auto-protection refusal, busy refusal, close, replacement generation, or main handoff. A late or forged YES cannot create membership or consume a newer unrelated invite. Existing process-wide coroutine social gate reproduces the source serial batch queue through asynchronous authority checks and ordered cache projection. No ordinary mutex may be held across `co_await`.

Wire limitation: the client answer carries no invitation nonce. A late answer for an earlier invitation is indistinguishable from an answer to a newer invitation with the identical origin/target/obtain tuple in the same live actor/Map generations. Generation fences and one-use pending consumption do not prove closure of that same-tuple ambiguity. It remains an explicit protocol limitation unless a compatible, concrete disambiguation strategy is implemented.

Source transfer completion clears `m_bPartyWaiter` (`SSHandler.cpp:1538`) while retaining same-character party membership. Native fresh generation and true logout remove membership through `CloseChar`; transferred state must project the party rather than creating a second member. Party IDs can be recycled, so stale local projection/dialog state also needs generation/current-World connection safeguards.

Source readiness boundaries are distinct. `World SSHandler.cpp:1038–1092` marks `ENTERCHAR_ACK` connection readiness and calls `CheckMainCON`; `CHECKMAIN_ACK:1095–1185` either sends `CONRESULT`/pops the connection queue, or starts main release. Normal `ENTERSVR_ACK:1343–1358` clears the prior-main flag and requests the Map server list. Original Map `CSHandler.cpp:402–415` handles client CONREADY locally through `InitMap`/`EnterMAP`, with no World ready acknowledgement. Native `OnCheckMainAck` finalizes its actual winning handoff, while native SQL readiness happens later in Map `handlers/session.cpp` at `MarkReady` commit and Ready transition. A post-CONRESULT transport write is not that SQL readiness proof.

### Target invite projection, JOIN and ATTR

Map `SSHandler.cpp:7839–7921` consumes target DWORD char/key, STRING origin/target, BYTE obtain/result, DWORD inviter. Missing/main-less/map-less target responds ASK_BUSY with four zero stats (a failure branch, never successful stats). Terminal result projects `CS_PARTYADD_ACK`. Agreed invite checks actual `IsActionBlock`, then `CheckProtected(inviter,PROTECTED_INVITE=2)`; these yield BUSY/NO respectively. Otherwise send `CS_PARTYJOINASK_ACK` STRING origin + BYTE obtain. Native protection must read the current `TPROTECTEDTABLE` bit under actor authority.

World `SSSender.cpp:716–748`, Map `SSHandler.cpp:7923–7992`, Map `CSSender.cpp:1729–1769`, and client `CSHandler.cpp:4937–4974` agree on JOIN: prefix DWORD recipient/key only on MW, followed by WORD party, STRING member-name, DWORD member, DWORD chief, WORD commander, STRING guild-name, BYTE level, four DWORD stats, BYTE race/sex/face/hair/obtain/class. Source client appends that member to its roster. Duplicate JOIN replay therefore must be avoided.

`JoinParty` traverses existing members in insertion order: joining target receives each existing member; each existing member receives joining target. Membership/backlink is added after the pairwise source fanout, followed by target `PartyAttr`. A fresh party adds origin first (self ATTR without a self roster JOIN), then target (the two mutual JOIN messages, then target ATTR). Modern mutation/fanout hardening must preserve client-visible ordering and close/reconcile on uncertain writes instead of replaying partial roster success.

`PartyAttr` (`World TWorldSvr.cpp:2882–2927`) sends to main plus every other valid Map connection. MW body: DWORD recipient/key, WORD party, BYTE obtain, DWORD chief, WORD commander. Native role resolution must use full typed Map IDs, not low-byte matching of arbitrary peers. Map ATTR (`SSHandler.cpp:10429–10505`) mutates all local copies; only main sends `CS_PARTYATTR_ACK` (DWORD subject, WORD party, DWORD chief, WORD commander) to own client and spatial neighbors. Main/replica authority is therefore distinct from the primary-only CS initiator gate.

Source also leaves arena queues on party0 and teleports a departing main out of `MAP_INDUN` using `GetIndunOutPos`. Those downstream arena/instance behaviors require their actual systems and remain OPEN if unavailable; a generic party attribute is not their completion.

### Departure, dissolution and stats

`World TWorldSvr.cpp:2990–3058`: when size>2 or `bDelete=false`, the party survives; departing chief selects the first other member in insertion order (`TParty.cpp:125–143`). Source broadcasts updated ATTR to every current member before DEL when chief changes. Normal size<=2 departure sets chief0, sends DEL to all members, removes the departing member, ATTR0 to that member, recursively leaves the remaining member with `bDelete=false`, then deletes the party.

DEL MW: DWORD recipient/key/member/chief, WORD commander/party, BYTE kicked (`World SSSender.cpp:749–768`). Original Map `SSHandler.cpp:7994–8031` reads the received chief/commander/party but emits client DEL using its current cached attributes, without updating them. ATTR owns cache changes. Client `CSHandler.cpp:4976–5019` removes another member, or clears its entire roster and party attributes for self. This source ordering/cached-tail detail must be explicit in any modern projection.

`CloseChar` source `TWorldSvr.cpp:3061–3084` leaves party before deleting the character. Native cleanup must invalidate invites pointing at that exact TChar generation, update both party and char backlinks, and avoid applying late sends to a replacement generation. World monitor `m_mapACTIVEUSER` is historical unique admitted users: source adds at `SSHandler.cpp:722–724`, resets only through service data clear (`135–145`), and does not erase on `CloseChar`. Removing a party player must not shrink that history.

`Map CSSender.cpp:1315–1335` sends `MW_PARTYMANSTAT_ACK` whenever own `CS_HPMP_ACK` is sent while in a party. Body WORD party, DWORD member, BYTE type/level, four DWORD stats. World `SSHandler.cpp:2840–2903` updates the identified member's combat stats and relays `MW_PARTYMANSTAT_REQ` to each main member; additionally to corps general for a chief. Map `SSHandler.cpp:8033–8075` strips recipient/key and sends exact client stats; client `CSHandler.cpp:5060–5096` updates the roster. Basic native party requires this ongoing HP/MP supplier rather than only invite-time bars. Corps-general relay remains dependent on corps authority.

Native group4 now uses the actual transient party, typed current primary routes, source chat sender/ban/spam/country/text/frame gates, and each recipient's protected-chat bit1. Guild/tactics/corps and BR local-team routing remain OPEN.

## Native authority and implementation review boundaries

At baseline, Map `handlers/social.cpp` decodes/logs ADD/JOIN/DEL stubs. World `handlers_party.cpp` has process-local source-inspired handlers but low-byte peer lookup, no native actor/generation authority, boolean waiter, and asynchronous fanout before membership updates. These are the concrete production gaps of the selected continuation.

Existing `communication_authority.h` uses typed0x0400|server current primary, open peer, exact TChar pointer/key, ready/valid connection and no close/logout/loading state; after SQL offload it rechecks the cache. `PostgreSQLFriendRepository::GuardActor` additionally verifies current user, current primary phase, Map token/backend advisory lease, undeleted char and World owner transaction. Party needs all involved members' current authority and sorted unsigned account locks, not only the packet sender; liveness may change across each await. Self-contained process-local mutation must remain serialized with `CloseChar` and handoff.

World identity fields are populated from real Map `ENTERSVR_ACK` (`handlers_char.cpp:278–344`); real four stats arrive in successful ADD/JOIN/MANSTAT. Native Map `postgresql_map_load.cpp:497–500` explicitly rejects any persisted `app_world.guild_membership`. Thus accepted native basic-party actors can be authoritatively guildless, with exact `NAME_NULL`; missing hydration must not silently substitute guildless for a guild member. Full guild member loading remains OPEN.
