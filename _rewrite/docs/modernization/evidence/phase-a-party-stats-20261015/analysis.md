## Finding: basic party membership is not a statistic formula input

The previous `PostgreSQLMapService::RefreshEquipment` (`Server/TMapSvrAsio/services/postgresql_map_load.cpp:397` at baseline) rejected any raw `s.cluster.party`. This blocks the existing native equipment, skill validation, item-use, quest reward and level derivation paths even for a guildless ordinary party with supported effects. Original getters do not condition their formulas on party ID or roster:

## Companion, recall, local and soulmate boundaries

Original `TPlayer.cpp:659` resolves the actually selected companion slot. `CalcPetATTR` at5665 returns zero only when there is no actual selected companion. Otherwise it adds its six WORD stats and a BYTE accumulator over owned companions: each contributes1, with an additional5 for level≥11 and life≥2400. `CalcPetBonus` at5700 requires a selected companion, the matching bonus catalog, a matching bonus ID with life≥2400 and either level≥11 or selected slot; it returns FLOAT base + multiplier × (level−1) for the first matching row. MMP, attack/defense levels and critical/charge getters contain explicit companion additions. An empty cached statistic sheet or an unknown companion graph cannot stand in for these inputs.

Native `CharacterPayload::pets` comes from account-owned `TPETTABLE`; it is inactive pet inventory, not proof of a selected companion or an active recall. Active `p.recalls` and transferred companion/recall/buff/item graphs are different. Existing source-format transfer retains them; supported stat derivation must reject them until their producers and authoritative hydration exist. The existing local ID is a WORD and is associated with local/battle lifecycle (`TPlayer.cpp:2131` and transfer source fields); rejecting a nonzero local graph is a conservative unsupported-context boundary, not evidence that local ID appears in HP/MP arithmetic. Guild and recall restrictions likewise preserve the existing unsupported production graph boundary rather than invent a party bonus.

Soulmate is separate from the maximum-stat formula. `TPlayer.cpp:4686` `CheckSoulHP` is invoked by the positive-damage HP path (`TObjBase.cpp:752`). It excludes duel/tournament paths, requires the injured actor alive and below DWORD-truncated15% of actual max HP, scans actual neighbors, and accepts a main donor with matching directed soulmate, no silence and the same nonzero effective party. `TransSoulHP` at4740 requires the donor alive/main/on-map and above DWORD-truncated65% of its actual max HP, removes all excess above that threshold, and caps the receiver at its actual max HP. `CheckSoulEXP` at4667 is called by the actual monster reward path (`TMonster.cpp:674`), uses alive/current main soulmate in the supplied party audience and DWORD-truncated10% of actual EXP. These cross-actor HP/XP producers remain OPEN; permitting a supported actor's local equipment/level derivation does not implement them or fabricate recipients from an unknown roster.

## Implemented bounded native statistics change and static review

Development added a shared `SupportedStatisticsContext(s,p)` in `postgresql_map_load.cpp` and uses it in both sheet construction and equipment refresh. It requires known `SupportedPostures`, no guild and no active payload recalls; a transferred graph additionally requires empty companions, companion items, recalls and recall buffs, plus local ID0. A missing payload or missing existing source-derived sheet rejects refresh. `SupportedPostures` (`services/posture_effects.h:16`) requires an actual effects vector and only rank1 permanent automatic postures131/132 or specifically pinned validated progression/probability statuses; it is not a wildcard acceptance of unknown/group buffs.

The old raw party-ID refusal is replaced by those concrete graph requirements. The existing `DeriveStats` clears `p.statistics` before reloading pinned posture/progress definitions and building a new sheet. The new post-derive nonnull requirement therefore cannot pass using a stale prior sheet. Refresh preserves original raw item projection, hashes and alarm metadata; no unknown default statistics, fake roster, new opcode or party-wide SQL mutation is introduced. This static review found no additional blocker in that bounded change. Existing native transaction, claim/catalog checks, immutable graph receipts and post-commit cache publication remain the authority boundary; the new helper is not a substitute for them.

Call sites include `ValidateSkillCast` (`postgresql_map_cast.cpp:52`), equipment moves (`postgresql_map_inventory.cpp:89/140`), item-use (`postgresql_map_item_use.cpp:150`), progression (`postgresql_map_progression.cpp:100/127`), during-items, quest item/reward effects, item economy/shop/gamble/upgrade/expiration and checkpoint stat-changing mutations. This shared removal of an unsupported blanket assumption does not make every caller or all party combat complete. Original level gain recalculates/fills actual bars and emits a direct party status producer (`TPlayer.cpp:1314–1330`); native progression already carries the actual intermediate level/bars. Original `CSSender.cpp:1315` emits party MANSTAT only when the HPMP subject is the sender itself and effective `GetPartyID()` is nonzero; SOLO remains masked. Own HPMP body is actor DWORD, type BYTE, four DWORD bars, with no level BYTE; original MANSTAT adds party WORD and level BYTE. `CS_CHARSTATINFO_ACK` at3241 includes six WORD-converted primary stats and the actual DWORD/WORD/BYTE secondary fields. These layouts are unchanged by the context gate.

## Additional bounded World continuation: actual unsent departure deltas

Root implemented process-local retention of actual `MW_PARTYDEL_REQ` events that were never attempted because the target actor was in a handoff or its current route was not ready. This does not reconstruct a complete roster and does not manufacture a self DEL as a reset.

Source `TWorldSvr.cpp:3026–3064` broadcasts to the pre-removal ordered members. `SSSender.cpp:749` writes recipient DWORD, key DWORD, departed member DWORD, chief DWORD, commander WORD, party WORD and kick BYTE. The leaver receives chief/party0; survivors receive the actual successor chief/party or0 for dissolution. The source then removes the member, sends the actual leaver ATTR, and recursively removes the remaining actor for a two-person dissolution. The two actual events for the last actor must retain order: departure of the first actor, then its own actual departure. Source client `CSHandler.cpp:4976` removes the specified member row; self departure calls `ReleaseParty()` at5014. This is why invented self DEL would destroy valid rows.

Crucial source nuance: Map `SSHandler.cpp:7994` parses World chief/commander/party but does not mutate its cache and constructs `CS_PARTYDEL_ACK` using its **current cached effective** chief/commander/party getters. Native Map `handlers/social.cpp` retains that behavior. A pending event must therefore flush before the registry's actual final ATTR; the final ATTR repairs current metadata but is not a roster reset or delivery acknowledgement. Deferred succession can expose older cached metadata during the DEL and then current metadata in ATTR; this is an explicit modern recovery ordering limit rather than full original batch equivalence.

Static review of the actual implementation: `DeferredPartyRemoval` stores the original member/chief DWORDs, commander/party WORDs and kick BYTE on the same live `TChar`, and only native corps0 records an event before a failed current-route gate or behind an already pending event. The actor must remain the same indexed object/key and not closing/logout. `FlushDeferredPartyRemovals` requires the caller's `party_operations` permit and successful native Ready proof; it removes the FIFO front before invoking the single original sender. It does not catch and reinsert attempted/failed/unknown output. Its loop rechecks exact current main/character/key between awaits. Neither the vector nor party membership claims SQL persistence, and object retirement discards that process-local state.

Ready repair independently proves a primary or the exact ready replica→primary token/connection/epoch relationship before draining to the actual primary. A concrete review defect was corrected: a replica trigger originally drained DEL to the main but sent the final ATTR only to the replica, leaving the main with the old cached chief. Root now captures `had_deferred` under the actor lock; `primary || had_deferred` uses `SendAttr` to publish actual current metadata to the main and every valid Ready route. A replica-only metadata refresh without pending departures retains its original narrow destination. No fabricated member packet, self reset, or application acknowledgement was added.

Another concrete limit handed to root was implemented through `party_authority::CanMutate`: an actor cannot accept a new join/new party while older departure events are pending. An old actual self DEL would otherwise erase newly appended JOIN rows; an old other-member DEL could erase the same character rejoined later. Guards cover inviter/target ADD, JOIN, existing roster preflight and chief/type, manual leave/kick issuer and target, and ATTR publication. SendAttr waits behind pending DEL, while the native Ready proof deliberately remains callable to drain it. Gate nesting is unchanged: refresh acquires `party_operations` once; its FIFO/ATTR helpers do not acquire it recursively. Existing handoff-main mutation also takes that gate; no mutex is held across packet/SQL awaits.

The original initial ENTERCHAR_ACK branch additionally tries native Ready repair after recording the reporting World connection Ready and before its all-ready CheckMain decision. A merely loaded SQL claim cannot pass the Ready proof, so this does not promote client or SQL readiness or produce a fake CONRESULT. A final review finding was corrected: after the newly awaited repair, the branch rechecks the same indexed actor, current typed/open peer, key, not closing/logout, allowed handoff Confirm phase and the reporting valid/ready connection; it recomputes all-ready under the actor lock before CheckMain. The earlier local snapshot is no longer reused across that await. Blind JOIN replay, missing complete-roster recovery, output acknowledgement, process restart retention and arbitrary missed attempted packets remain OPEN.

## Independent high-bit identity audit, no implementation claim

Saved original backup schema metadata describes `TACCOUNT_PW.dwUserID` and `TCURRENTUSER.dwKEY` as signed SQL Server INT, four bytes (`backup-schema.json:312/6633`); original `TGLOBAL.TLogin` uses INT output parameters. Wire/client/server identity types are DWORD. Native World social code explicitly preserves the signed bit pattern. In contrast, baseline Map `postgresql_map_service.cpp:45/53/67` binds user/key/character DWORDs as positive `long long` in LockAccount, LockClaim and LookupSession; `postgresql_map_replica.cpp:59` does the same for replica admission. A stored negative signed INT cannot equal that widened positive value. A fix to one gameplay writer cannot solve the initial claim failure.

There is an additional schema boundary: `database/postgresql/012-native-characters.sql:24` declares native `dwCharID integer CHECK(dwCharID>0)`. Therefore binding fixes alone cannot honestly establish the entire DWORD character-ID domain. This audit records the mismatch and the separate migration/identity-policy decision; it does not infer missing backup values or claim that the current pinned data exercises a negative ID. Any later fix must distinguish signed bit-preserved32-bit user/key/character IDs from actual nonnegative BIGINT connection IDs/epochs, endpoint IP storage and other unrelated numeric domains. No SQL or new backup inspection/extraction was run.
