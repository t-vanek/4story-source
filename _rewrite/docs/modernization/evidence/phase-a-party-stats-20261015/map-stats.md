# Native Map party statistics — 2026-10-15

Baseline: `b251cdf`. Status: **IMPLEMENTED / INTEGRATED_UNVERIFIED**. Only static source, API, SQL-text and diff review was performed. No build, test, server/client/service, SQL statement, migration, import, extraction or runtime acceptance was executed. The Map agent created no commit or push.

## Source boundary

Basic party membership is not a statistic formula input. Original `TObjBase.cpp:2011–2035` derives HP/MP maxima through `Calc2ndAbility` (`1558`), virtual primary getters and item/skill modifiers. `TPlayer.cpp:5739–5765` adds the real companion attribute contribution to CON/MEN; `CalcPetATTR` (`5665–5698`) and `CalcPetBonus` (`5700–5723`) read actual selected companion state. `CalcAbilityValue` (`TObjBase.cpp:1409–1450`) uses instance, maintained and passive skill effects; `ApplyEffectionBuff` (`4247–4272`) additionally reads actual maintained MAGIC statuses. These paths do not read party membership or its roster.

`CalcItemAbility` (`TObjBase.cpp:1624`) uses real equipment state, including powered/broken items and disguise/disarm semantics. The native pinned posture/progression subset already validates its actual skill templates and effects; arbitrary maintained graphs remain unsupported. Guild/local, active companion and recall producers are separate unported capabilities. Inactive account-owned TPET inventory is not an active companion statistic supplier.

Soulmate HP sharing (`TPlayer.cpp:4686–4780`) reads effective party membership and nearby actors, but it is a cross-actor HP mutation producer, not the definition of GetMaxHP/GetMaxMP. Soulmate party-monster XP sharing (`4667–4684`) is also a separate producer. This change implements neither of them.

## Concrete native path

Previously `PostgreSQLMapService::RefreshEquipment` rejected every nonzero raw `cluster.party`, even when the actor already had a valid source-derived statistic sheet and no unsupported graph. Equipment moves reach it from the existing network inventory handler through the current checkpoint/claim transaction, `ValidateInventoryMove`, item projection and `ApplyEquipmentPostures`. Item use, equipment mutation, expiration, progression and quest rewards also use this same derivation boundary. The blanket rejection could therefore abort otherwise supported native gameplay simply because a basic party had been joined.

`postgresql_map_load.cpp` now shares `SupportedStatisticsContext` between statistic derivation and equipment refresh. It accepts only a supported maintained/posture graph, no guild metadata, no actual recall rows, and no transfer companion/companion-item/recall/recall-buff/local graph. `RefreshEquipment` still requires an existing supported sheet and a complete native payload. A requested rederivation must produce a new supported sheet before publishing the copied payload; it cannot silently erase the sheet and continue with zero/default statistics. Additional empty orphan companion/recall subgraphs are conservatively refused rather than interpreted as a fabricated inactive state.

Raw/effective party id, chief, type and roster are not rewritten or assumed zero. SOLO1 does not select another formula. Actual level/class/race, powered item attributes/magic, learned/passive skills and supported active postures still drive all values. Existing native ownership, catalog publication, current login/claim, checkpoint revision, atomic mutation and unknown-write confirmation/no-replay boundaries are unchanged. No new wire field, opcode, SQL schema or grant was added.

The existing inventory response path sends its committed equipment display and actual HP/MP through `PublishPartyVitals`; independent level-up and other already wired own HPMP producers remain intact. This is a supported statistic-context repair, not full party combat, equipment, loot or effect acceptance.

## Independent high-bit identifier audit — OPEN, no implementation

The archival schema uses signed PostgreSQL `integer` for the bit patterns of source DWORD user/key/character identifiers (`002-legacy-snapshots.sql`: TACCOUNT_PW, TCURRENTUSER, TCHARTABLE). Native account/session keys are integer identities (`008-native-login.sql`: TACCOUNT_PW and TCURRENTUSER, GENERATED BY DEFAULT); `016-native-map-ownership.sql` stores `map_sessions.char_id/user_id/session_key` as integer; replicas (`019`) reference that character key; transfers (`020`) also use integer identity columns. Connection generations and authority epochs are genuinely positive `bigint`, and endpoint IPv4 is a genuinely unsigned-range bigint: these must not be treated as signed DWORD identities.

Native characters have an additional independent range boundary: `012-native-characters.sql:24` defines GENERATED ALWAYS integer `dwCharID` with `CHECK (dwCharID>0)`. Thus a negative integer representing a high-bit character DWORD cannot currently be provisioned there at all. A Map binding fix would not establish complete character-ID coverage or authorize changing this schema/sequence policy. Archival bit preservation, explicit account/session bit patterns and native character allocation must be reviewed separately.

Static blockers remain:

| Boundary | Current binding | Consequence for a high-bit DWORD |
| --- | --- | --- |
| `postgresql_map_service.cpp`: LockAccount, LockClaim, LookupSession, ClaimSession, CloseClaim | unsigned DWORD widened to positive `long long` | Does not address the same negative integer bit pattern; admission, authority or clean release can fail |
| `postgresql_map_replica.cpp`: ClaimReplica, LockReplica, ReleaseReplica | same positive widening | Replica claim/projection/release has the same mismatch |
| `postgresql_map_load.cpp`: LoadAuthorized and loaded-phase updates | same positive widening | Fixing shared account/claim locks alone would leave hydration inconsistent |
| `postgresql_map_checkpoint.cpp`: ReadReceipt, MarkReady/RecordCheckpoint and core writers | several positive `long long` identity bindings | A partial ingress fix would still break checkpoint/readback/write or unknown-commit confirmation |
| `postgresql_map_transfer.cpp` | many identity locals are signed `int`, recovery reads signed rows then restores DWORD bits | Those local conversions are consistent in C++20, but the shared positive account/claim fences still prevent full support; mixed downstream binds need one coherent review |

Party/chat/social-specific queries already use explicit `std::bit_cast<std::int32_t>` in several places, but they cannot bypass the shared incorrect account/claim bindings. A safe follow-up must consistently convert only source DWORD identity columns across admission, replica, hydration, checkpoint, handoff, confirmation and release, retaining genuinely wide counters/IDs and all exact authority predicates. It needs deferred boundary acceptance at `0x7fffffff`, `0x80000000`, `0xffffffff`, zero refusal, mixed high/low actor pairs, owner takeover and unknown commit confirmation. This audit alone is not proof of full DWORD support, and no identifier code was changed here.
