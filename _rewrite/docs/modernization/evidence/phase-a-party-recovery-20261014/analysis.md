## Implemented bounded native recovery and static review

The implemented direction repeats the existing `MW_ENTERCHAR_ACK {DWORD char_id, DWORD key}` once after actual SQL `MarkReady`, local Ready transition, and presence binding, for both primary and replica. This is a **modern post-CONREADY metadata repair using an existing source opcode/body**, not an original source Ready ACK. The native World branch recognizes an already-ready current typed Map connection, serializes through `party_operations`, proves current PostgreSQL primary/replica authority, and sends the registry's actual `MW_PARTYATTR_REQ`, including actual party0. It does not repeat CheckMain, CONRESULT, registry readiness mutation, JOIN roster rows, or invented vitals. The original initial entry branch and the explicit legacy/test adapter remain separate.

Static review of the new PostgreSQL proof observed the following lock order: World owner transaction fence; sorted primary and target Map owner rows with actual live advisory lease checks; unsigned/deduplicated account row locks; current ready primary claim/current-user/character share locks; ready replica share lock. `AuthorizePartyReplica` joins the replica's recorded primary server/token/connection/authority epoch to the actual ready primary row and the target token to its current Map owner; returned primary and target tokens are compared with the exact registered `PeerSession`s before sending. The source actor key, unlocked current user, canonical wire name, guildless supported graph, typed peer/open/current registration, and no-handoff lifecycle are required. The Map receiving projection must independently retain its exact ready primary/replica connection and SQL generation fence; the World probe must not grant replica write authority over primary persistence.

The actual Map `RefreshReadyParty` in `handlers/social.cpp` checks the immutable native PostgreSQL adapter capability, actual Ready identity and hydrated/non-uncertain snapshot, then authorizes that exact primary/replica and writes the original eight-byte identity body. Legacy adapters do not start emitting new probes. The normal admitted→Ready path calls it after durable/local Ready and presence publication; the retained-source transfer→replica path calls it only after the actual transfer receipt and local role/epoch transition. Repeated client CONREADY while already Ready retains its previous no-op behavior. No statistics supplier, DTO field, or unknown replica bar is needed.

World `handlers_conn.cpp:OnEnterCharAck` validates the exact two-DWORD body, EOF and current typed Map. The native already-ready connection branch calls `handlers_party.cpp:RefreshReadyParty` and returns. The helper holds the party operation gate, independently proves primary or ready replica ownership, checks actual registry backlinks and supported corps0, then sends ATTR. It does not invoke CheckMain again. Non-native duplicate entry ACK behavior remains the previous adapter behavior; it must not be mistaken for the original source's duplicate-ACK CheckMain behavior. The obsolete `party_refresh_needed` cache flag was removed; real MANSTAT remains a real status producer and does not synthesize the ready probe.

Constructor probes and `deploy/sql/world-social-runtime-grants.sql` cover the newly read replica columns and `SELECT, UPDATE(char_id)` permission needed for PostgreSQL `FOR SHARE`. The new World path reads existing ownership tables and does not issue replica grants, mutate replica ownership, or add a migration. Function declarations, `FriendAuthority` field ordering, `PartyIdentity` equality and awaitable return types were inspected statically. This is not compiler or SQL execution evidence.

Two concrete lifetime findings were handed to development and addressed in source. First, the primary CONREADY admission operation initially survived through the new ready probe and all AOI/quest awaits: an immediate ATTR could then wait on the three-second projection deadline. The operation now resets after committed Ready/presence publication and before recovery/flood awaits. Second, the original AOI loop encoded a cached pre-Ready snapshot once across sends: an ATTR arriving before ENTER could be ignored by an unseen client actor, then a stale ENTER could publish old metadata. The loop now samples the actual live actor under a short `BeginGameplay`/`SessionOperation` lease for each enqueue. Actor and recipient identity/role/epoch/current Ready checks surround waits; the two actor leases occupy separate scopes and do not accumulate across the flood. The own→neighbor recipient is rechecked after the awaited actor lease and before enqueue. A narrow post-acquisition expected-identity recheck was suggested because `BeginGameplay` itself checks phase/checkpoint rather than the complete expected tuple. No runtime timing or client application claim is made.

World `OnCheckMainAck` acquires the party operation gate before changing main server or handoff phase. After waiting it checks the same actor, key, current typed/open peer and requested valid/ready connection again. It releases the permit before RELEASEMAIN, CONRESULT and `PopConCess`; the latter's cleanup may itself retire a party. Refresh and chief/type helpers call DB proof/ATTR helpers without acquiring the same gate recursively. The existing chat order remains communication gate→party gate, without a reverse acquisition. Close/Leave during another actor's handoff can still lose a roster delta; this remains an explicit recovery dependency, not a reason to replay JOIN or invent DEL.
